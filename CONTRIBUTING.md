# Contributing

## Development setup

Install the dependencies:

```sh
npm install
```

Build commands:

| Command | What it does |
| --- | --- |
| `npm run dev` | Builds `main.js` in watch mode with inline sourcemaps |
| `npm run build` | Type-checks with `tsc`, then builds a minified `main.js` |
| `npm run lint` | Lints `main.ts` with ESLint, using `eslint.config.mjs` |

All the plugin code is in `main.ts`. `main.js` is generated by the build and is ignored by git.

## Testing in Obsidian

There are no automated tests. To test a change by hand:

1. Use a test vault, not your real one.
2. Copy `main.js`, `manifest.json` and `styles.css` into
   `<vault>/.obsidian/plugins/outlook-meeting-notes/`. You can also symlink the repo
   folder there and run `npm run dev`, so that every rebuild lands in the vault.
3. Enable the plugin under **Settings → Community plugins**. After each rebuild, reload
   Obsidian or turn the plugin off and on again.
4. Drag a meeting from Outlook Classic onto the ribbon icon. On a machine without
   Outlook, drop a saved `.msg` appointment file instead.

If you change a template helper or a setting, update the user documentation in
[README.md](README.md). The plugin's settings tab links to it.

## Releasing

1. If the release needs a newer Obsidian version, update `minAppVersion` in
   `manifest.json`.
2. Bump the version:

   ```sh
   npm version patch   # or minor / major
   ```

   This updates `package.json`, `manifest.json` and `versions.json`, commits the
   changes, and creates a tag. The tag is the bare version number, such as `0.2.2`,
   because `.npmrc` sets an empty tag prefix and Obsidian doesn't accept a `v` prefix.
3. Push the commit, then push only the new tag:

   ```sh
   git push
   git push origin 0.2.2   # the version npm just created
   ```

   Don't use `git push --tags`. It pushes every local tag, and GitHub doesn't trigger
   workflows for tags when more than three are pushed at once, so no release gets built.
4. Pushing the tag runs [the release workflow](.github/workflows/release.yml). It builds
   the plugin and creates a **draft** GitHub release with `main.js`, `manifest.json` and
   `styles.css` attached. Drafts only appear on the Releases page for people with write
   access, and not in the repository sidebar.
5. On GitHub, add release notes to the draft and publish it, or run
   `gh release edit <tag> --draft=false`.

Obsidian users get updates from the releases on the repository registered in the
[community plugin list](https://github.com/obsidianmd/obsidian-releases). For this plugin,
that is `davidingerslev/outlook-meeting-notes`.

## Working in this fork

This repository is a fork of
[davidingerslev/outlook-meeting-notes](https://github.com/davidingerslev/outlook-meeting-notes).

### Branches

- `master` mirrors upstream's `master`. Don't commit to it directly.
- `dev` is the default branch and is where this fork's work goes.
- Create topic branches from `dev`, named `<type>/<short-description>` (for example
  `fix/yaml-escaping`), and open pull requests against `dev`.

### Syncing with upstream

The fork needs a remote for upstream (one-time setup):

```sh
git remote add upstream https://github.com/davidingerslev/outlook-meeting-notes.git
```

To bring in upstream changes:

```sh
git fetch upstream
git switch master
git merge --ff-only upstream/master
git push origin master

git switch dev
git merge master
git push origin dev
```

### Contributing changes back to upstream

Create a branch from `upstream/master` that contains only the commits you want to send.
Then open a pull request against `davidingerslev/outlook-meeting-notes`. Leave out
fork-only files such as this section and `CLAUDE.md`.

### Releases from this fork

Fork releases use the upstream version that `dev` is based on, plus a `-fork.<n>` suffix.
For example, `0.2.1-fork.1` and `0.2.1-fork.2` are the first and second fork releases
based on upstream `0.2.1`. The release workflow reads the upstream version from the tag.
It titles the draft release `0.2.1-fork.1 (based on upstream 0.2.1)` and links to that
upstream release in the release notes.

To release from `dev`, follow the [Releasing](#releasing) steps, but bump the version
like this instead of using `npm version patch`:

- **First fork release after syncing with upstream:** write the version out, because
  `npm version prerelease` would bump the patch number of a plain upstream version:

  ```sh
  npm version 0.2.1-fork.1
  ```

- **Later fork releases on the same upstream base:**

  ```sh
  npm version prerelease --preid=fork   # 0.2.1-fork.1 → 0.2.1-fork.2
  ```

The workflow fails if the tag doesn't match the `version` in `manifest.json`.

When you sync with upstream after a fork release, merging `master` into `dev` conflicts
on the `version` in `package.json` and `manifest.json`. Keep upstream's version there.
`versions.json` keeps both sets of entries.

Obsidian's updater never sees releases from this fork. They're for your own use: install
them by hand or with [BRAT](https://github.com/TfTHacker/obsidian42-brat).
`manifest.json` still has upstream's plugin `id`, so installing a fork build replaces the
official plugin in that vault.
